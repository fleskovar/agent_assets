# Examples: cases that pass review, and four that do not

The accepted example is `cases/overdue-invoice-fees/` — read it first, in full.
What follows is the same case seen from the reviewer's chair, then four rejected
variants with the specific reason each fails. The rejections are the useful part:
every one of them is a real thing people submit.

---

## Accepted: `overdue-invoice-fees`

Why it passes:

- **Human-solvable in about four minutes.** Seven rows, integer minor units, a
  25 bps rate that divides cleanly by 400. A reviewer can check every number.
- **Every row is justified** in the "why each row exists" table, and each one
  pins a different rule.
- **The boundary is pinned from both sides.** `INV-1003` at exactly 5 days and
  `INV-1007` at 6 days together make "grace is inclusive" impossible to break
  silently. One row alone would let an off-by-one through.
- **It pins an ordering that no type can express.** Minimum then cap — and the
  case has a row, `INV-1002`, where the two disagree. Without that row, reversing
  the rules changes nothing in the output and the test is decoration.
- **Rounding is pinned at a value that lands on exactly `.5`.** 562.5 → 563.
  Half-up and banker's rounding differ by one cent on precisely this input, and
  nowhere else in the case.
- **The clock is a file.** `as_of.json` — the case gives the same answer forever.
- **The walkthrough does the arithmetic** rather than describing the code.
- **The claim is bounded.** "It does not cover" names what property tests and
  integration tests are responsible for instead.
- **The history table** shows `INV-1006` arriving with a bug fix, which is the
  bug-fix workflow leaving its trail exactly where the next reader will find it.

The reviewer's question that this case answers well: *if I reverse two rules in
the implementation, does something go red?* Yes — and the reviewer can name which
row.

## Rejected 1: the baseline nobody derived

```markdown
## Baseline provenance
Generated by running `assess_late_fees` on the inputs and saving the output.
```

**Why it is rejected.** This proves the code does what the code does. If the
grace boundary is off by one today, this case makes the off-by-one permanent and
fails every correct fix for the next three years.

**What to do instead.** Derive by hand from the requirement, or name a genuine
oracle. If it really is a characterisation test around a refactor, say so
explicitly, and have a human justify every line first — then the case is honest
about describing *current behaviour* rather than *correct behaviour*.

## Rejected 2: production data as input

```text
inputs/invoices.json      4,812 invoices, exported from staging
outputs/assessed_fees.json 3,190 fee records
```

**Why it is rejected.** Nobody can solve it, so nobody reviews it. The first
time it goes red the diff is 800 lines and the response will be regeneration.
It is also very likely carrying personal data into the repository forever.

**What to do instead.** Seven rows that each demonstrate a rule. Keep the volume
run if it earns its place, as a separate smoke test asserting a *shape* — "no
fee exceeds its cap", "count of assessed + skipped equals input count" — which
is a property test, and belongs in `skills/automatic-test-generation/SKILL.md`.

## Rejected 3: the walkthrough that narrates the code

```markdown
## Walkthrough
`assess_late_fees` iterates the invoices, calls `_assess_one` for each, filters
the results by type and sorts them by invoice id before returning them.
```

**Why it is rejected.** A reader gets this from the source in less time. Nothing
here would let them *check* the baseline, which is the one thing the README is
for. When the implementation is refactored, this paragraph becomes wrong, and
nothing turns red.

**What to do instead.** Number the rules, then walk each row through them with
real arithmetic — the accepted case's `INV-1002` section is four lines of
multiplication and one sentence about ordering, and it will still be correct
after any refactor that preserves behaviour.

## Rejected 4: three behaviours in one folder

```text
cases/billing-run/
    inputs/   invoices.json  policy.json  customers.json  smtp.json  ledger.json
    outputs/  assessed_fees.json  ledger_entries.json  emails.json  audit_log.json
```

**Why it is rejected.** A single failure cannot say whether the fee maths, the
ledger projection or the mail templating broke. The walkthrough would be a
chapter. And `smtp.json` says the unit under test reaches an external service, so
the case will be slow or flaky or both.

**What to do instead.** Three case folders — `overdue-invoice-fees`,
`fee-ledger-entries`, `dunning-email-copy` — each with its own walkthrough. Then,
if the wiring genuinely needs proof, one thin integration test asserting that the
orchestrator called each piece with what the previous one returned. That test
asserts wiring, not arithmetic; the arithmetic already has three cases.

## A reviewer's checklist

Run this before approving any case folder. It is the same list
`subagents/test-design-reviewer.md` applies at the design gate.

- [ ] Could I compute `outputs/` from `inputs/` by hand in under five minutes?
- [ ] Does every input row have a stated reason to exist?
- [ ] Is every boundary pinned from **both** sides?
- [ ] Is there a row where two rules disagree, so their ordering is pinned?
- [ ] Where does the baseline come from, and is that written down?
- [ ] Is there any ambient input left in the code — clock, uuid, random, env,
      locale, filesystem order?
- [ ] Is the output canonical: documented sort, stable formatting, nothing about
      the machine that produced it?
- [ ] Does the walkthrough contain arithmetic and rule names, or a paraphrase of
      the implementation?
- [ ] Does the README say what this case does **not** cover?
- [ ] Can I run just this case, and debug just this case, from the commands in
      the README?
- [ ] Has someone broken the implementation and watched this case go red?
